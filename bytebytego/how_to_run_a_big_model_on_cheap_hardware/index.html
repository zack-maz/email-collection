How to Run a Big Model on Cheap Hardware

Quantization, offloading, MoE routing, distillation, pruning, and speculative decoding — each technique explained through the memory problem it solves.

The Memory Problem

An AI model is a collection of numerical values called weights (or parameters). An "8B model" has approximately eight billion of them. During inference — using the model to answer questions — these weights pass through the processor repeatedly, one generated token at a time.

The hardware constraint is simple: weights must fit somewhere accessible enough to be useful. There are three places they can live, each faster and more expensive than the last.

Key insight

A model that fits in memory can still be too slow to use. Memory bandwidth — how quickly the processor can read the weights — is often the real bottleneck for single-user text generation.

Two stages with different bottlenecks

Inference has two phases. During prefill, the model processes the entire prompt at once — lots of parallel work, GPU-bound. During decoding, it generates tokens one at a time — memory bandwidth-bound, because the full model must be read for every single token.

This means a model can be fast at understanding a long prompt but painfully slow at generating a short reply. Throughput and latency are separate concerns.

Quantization

Every weight is a floating-point number. At 16-bit (FP16 or BF16) precision, each weight takes 2 bytes. Quantization maps those high-precision values onto a smaller set of discrete codes — fewer bits per weight, less memory consumed.

The analogy: a weather forecast that says "73.4°F" and one that says "73°F" convey nearly the same information. The approximation introduces a small error — the question is whether the task tolerates it.

The tradeoff

Quantization does not change the number of parameters. It changes how much space each one takes. Quality can degrade — by how much depends on the model, the quantization method, and the task. Math and precise reasoning tend to suffer more than general conversation.

Note

4-bit storage doesn't guarantee 4× faster inference. Many engines dequantize to FP16 before the matrix multiply. Actual speedup requires hardware with native low-bit support (e.g. NVIDIA Turing+ INT4 tensor cores).

Post-training vs. quantization-aware training

Quantization can happen after training (post-training quantization, PTQ) with no re-training needed — just apply the scheme to the checkpoint. The alternative, quantization-aware training (QAT), bakes the approximation error into the training loop, which tends to recover more quality, but requires compute access to the original training pipeline.

Most practitioners start with an off-the-shelf PTQ checkpoint (GGUF Q4_K_M, AWQ, GPTQ) and measure whether output quality is acceptable for their task.

Layer-wise Offloading

Quantization shrinks each weight. Offloading changes where the weights live at any given moment. A transformer processes input layer by layer — and the GPU only needs the current layer's weights to do its work.

An offloading system keeps most weights in CPU RAM (or even on disk), transfers one layer to the GPU, executes it, and frees that GPU memory before loading the next. This lets a model whose total weights exceed VRAM still run on that GPU — at a cost.

The real cost

Every transferred layer adds latency proportional to its size divided by the transfer bandwidth. A 10 GB transfer over PCIe at ~10 GB/s costs ~1 second per decoding step. That's unusable for interactive chat.

CPU execution as a fallback

If no GPU is available, layers can be assigned permanently to the CPU. Generation is much slower — CPUs have lower memory bandwidth than GPUs — but the model runs. For batch workloads where latency doesn't matter, CPU-only inference is viable.

The practical takeaway: offloading expands what you can run, not what you can use interactively. Measure tokens-per-second before committing to an offloading configuration.

Mixture of Experts

Dense transformers send every token through every parameter. Mixture of Experts (MoE) is an architectural change: some layers contain multiple sub-networks called experts, and a small routing network selects which two (or k) of them process each token. The rest sit idle for that token.

This creates a distinction that matters for hardware planning:

  • Total parameters — determines storage size. All experts must be held somewhere.
  • Active parameters — determines per-token computation cost. Only the selected experts run.
The storage trap

A hypothetical MoE with 40B total parameters at 4-bit precision still needs ~20 GB of storage — the inactive experts sit in memory waiting to be selected. MoE reduces compute, not storage.

Distillation & Pruning

Knowledge Distillation

Distillation trains a smaller student model to mimic a larger teacher. The teacher's output distributions — not just its final answers — serve as training signal. The student absorbs behavioural patterns the teacher learned, not just the weights themselves.

The resulting student is a different model from the original, not a compressed copy. It may perform equivalently on the tasks the teacher was distilled for while falling short on problems the teacher handled through breadth or rare-knowledge recall.

When it works well

Distillation excels at narrow, high-volume tasks: routing support tickets, drafting short responses in a fixed format, classifying text. The student is trained once, then deployed millions of times on cheap hardware.

When it breaks

Don't assume a strong result on a narrow benchmark generalises. A distilled model that scores 95% on your test suite may fail unexpectedly on edge cases the teacher handled via memorised rare knowledge.

Pruning

Pruning removes weights — or entire structures — whose absence causes acceptable quality loss. Two flavours:

  • Unstructured pruning: individual weights set to zero. Creates sparsity. Rarely faster in practice — hardware still reads the zeroed entries unless the execution engine explicitly skips them.
  • Structured pruning: entire heads, layers, or feed-forward blocks removed. Smaller model on disk, fewer operations at runtime — straightforward speedup.
The execution caveat

Setting values to zero doesn't automatically save compute. An array with zeros still occupies memory. Actual savings require a compressed representation and an execution engine that knows how to skip the zeros — or structural removal that makes the model architecturally smaller.

Speculative Decoding

Decoding is sequential: one token at a time, each requiring a full model read. Speculative decoding exploits a different kind of parallelism — it uses a small, cheap draft model to propose several tokens at once, then uses the large model to verify all of them in a single forward pass.

If the large model agrees with a draft token, it's accepted for free. If it disagrees, everything from that point is discarded and the large model generates the correct token. The process restarts.

Why this helps

The large model's cost is dominated by memory bandwidth — reading its weights. Running one forward pass to verify N tokens costs almost the same as running it once to generate one token. When the draft model is accurate, you get multiple tokens per expensive forward pass.

KV cache: the other memory consumer

Even after shrinking the weights, context length creates a second memory problem. During generation, the model stores intermediate results from every previous token in a key-value cache. This cache grows linearly with sequence length and is separate from the model weights.

For long contexts (128K tokens) the KV cache can rival or exceed the weight storage itself. Techniques like grouped-query attention (GQA), multi-query attention (MQA), and KV cache quantization exist specifically to address this.
