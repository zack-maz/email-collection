How DeepSeek's n-gram memory tables reduce HBM pressure, why offloading them to DRAM wins, and what happens to a model when you pull its memory out.

Section 01

What is an Engram?

A standard MoE transformer processes each token in one direction: embed the token ID into a vector, run it through attention and feed-forward layers, predict the next token. Every piece of context must be reconstructed from scratch on each forward pass.

Engram adds a parallel lookup path. Before any layer runs, it searches a large learned table for n-gram keys — short sequences of recent token IDs. When a matching key is found, it retrieves pre-computed embedding vectors directly from the table, bypassing some of the attention and feed-forward computation needed to reconstruct that context.

The intuition: if the model has seen "Wright : Ace Attorney" ten million times in training data, there is no reason to recompute what those tokens mean together on every inference. The Engram table memoises the result. Recurring multi-token patterns are retrieved; novel combinations still go through full computation.

Why this matters for hardware: the Engram table in DeepSeek-V4.1-Flash weighs ~189 GiB. That is memory which, in a standard model, would have to live in HBM. Engram's lookup pattern — a small number of rows addressed by token ID, independent of hidden state — makes it uniquely suitable for offloading to cheaper memory without stalling compute.

Section 02

What Gets Memorized?

SemiAnalysis probed Engram's gate scores in DeepSeek-V4.1-Flash to find which n-grams the model relies on most. The results are a window into how the training objective shapes memory allocation.

The model does not selectively memorise "important" facts — it memorises whatever reduces prediction loss. Licenses, bibliography fragments, API scaffolding, and boilerplate web furniture appear heavily because they provide cheap prediction shortcuts: given MIT License, the next tokens are almost entirely determined.

Strong gate scores do not mean those rows are cache-hot at inference time. And low gate scores don't mean the rows are free to skip: computing the gate itself requires retrieving the key first, so a "skip" optimisation would need a separate usefulness predictor ahead of retrieval — a significant open research problem.

Important caveat: the gate scan uses the evaluation corpus, not training data. Finding a high-gate n-gram on the eval set proves the model uses that pattern, but does not establish that it was trained on it, nor how much table capacity it occupies. Gate strength reflects prediction shortcut value — not factual importance or semantic richness. High gates on boilerplate outcompete culturally significant but lower-frequency n-grams.

What this tells us about future Engram capacity: the value of a larger table depends heavily on what survives data preparation. If tokenization changes compress common boilerplate into single tokens, those table entries become worthless. Conversely, longer context windows or new domains introduce novel n-gram patterns the model has not yet memorised.

Engram is not a factual knowledge store — it is a pattern cache optimised by the training loss, which doesn't distinguish between "trivia worth knowing" and "filler worth predicting cheaply."

Section 03

What Happens When You Remove Engram?

The naive assumption is that Engram is a clean plug-in: memory on one side, reasoning on the other. Remove it, and the model degrades only on fact recall while reasoning stays intact. SemiAnalysis's ablations show the opposite.

Engram is woven into the model's computation graph. Its outputs change the hidden representations flowing into downstream expert routing. Removing it doesn't just cost you the lookup value — it changes which experts fire.

When SemiAnalysis forced the ablated model to use the expert selections from the Engram-on forward pass, performance got worse: 0.3375 bits/token vs 0.3093 for the clean ablation. The experts and the memory table have co-adapted during training. They are not independent modules.

Training–inference mismatch: DeepSeek's original paper ablated a model that was trained with Engram but ran inference without it. That measures the model's dependency on a feature it was optimised to use — not the performance of a model that never had the feature. The two numbers are very different.

Keeping Engram for prefill alone outperforms keeping it only for decode, likely because richer prefill hidden states produce a semantically denser KV cache that decode workers can use even without Engram on their side.

The takeaway: "memory stores facts, experts reason" is a clean division that doesn't hold empirically. Rerouting partially compensates for missing memory, but the compensation is lossy — the model was never trained to reason without its memory table in place.
Section 04

DRAM vs SSD Offload — Where the Engram Table Lives

The 189 GiB Engram table does not need to live in HBM. Its lookup addresses are token IDs — known before any layer computes — which means the fetch can be initiated while the GPU processes earlier layers. This prefetch window is what makes lower-tier memory viable.

SemiAnalysis tested three configurations on B200: HBM (baseline), pinned DRAM via Unified Virtual Addressing, and NVMe SSD via a memory-mapped file. The DRAM approach uses a GPU kernel that reads host memory directly through UVA, with async prefetch overlapping the fetch with preceding GPU work.

The surprising result: on B300 and week-0 stack, moving the Engram table back into HBM delivered no improvement and stayed within run-to-run variance. The optimised DRAM path is that good.

Why SSD costs more than you think: even with the Engram table fully cached in OS page cache (no physical SSD reads), the SSD path is slower than pinned DRAM. The bottleneck is not storage bandwidth — it's the CPU round-trip: copy row IDs to CPU, deduplicate, gather rows into pinned buffers, copy back to GPU, dequantize. UVA eliminates this round-trip entirely. A warm page cache still pays for coordination.

The TP reduction trick: offloading Engram to DRAM frees HBM capacity that was previously holding the table. That freed capacity allows a smaller tensor parallelism group — for example, B300 can switch from TP4 to TP2. Fewer GPUs per replica means less all-reduce communication per forward pass, which directly improves the throughput/latency Pareto by up to 1.6×. This is the hidden dividend of offloading: not just cheaper memory, but less coordination overhead.

HBM bandwidth vs capacity: with Engram offloaded, what matters for performance is no longer how much HBM you have, but how fast it is. 4-hi HBM stacks provide the best bandwidth-per-dollar. Model architecture innovations that reduce HBM capacity requirements could, at the limit, push toward 0-hi stacks — less memory physically stacked, all inference value coming from bandwidth.

Production verdict: SSD offloading is not currently worth the trade. Every measured SSD point on B200 has a DRAM alternative with higher P90 interactivity and more tokens per dollar. The SSD path might become viable with GDS (GPU Direct Storage), larger Engram tables that exceed available DRAM, or dedicated inference hardware designed around the access pattern — but none of those conditions exist today.
